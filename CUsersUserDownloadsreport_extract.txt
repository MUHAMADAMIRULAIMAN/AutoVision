3.2.1 Planning and Requirement Phase
The first iteration started with a planning phase aimed at understanding the day-to-day
operations at HICOM Diecastings. Through observations and a short interview with
the Head of Department, it became clear that the existing inspection process was prone
to fatigue-driven errors and had almost no centralised data tracking.
From these findings, three core requirements were locked in: the system had to
capture brake disc images in real time, automate sorting via a conveyor, and log every
inspection event to a centralised database for later analysis. The decision to use
Streamlit and Supabase was also made at this stage, mainly because both can be set up
by a single developer without dedicated infrastructure.

3.2.2 Analysis and Design Phase
The analysis and design phase bridged the gap between the high-level requirements
and the actual implementation. A modular architecture was drawn up where a central
Python script (dashboard.py) acts as the controller, mediating between the webcam,
the YOLOv8 model, the Arduino serial port and Supabase. The database schema was
designed around two tables: 'users' for credentials and roles, and 'inspections' for every
Pass/Fail event.
The dashboard layout was wireframed with operational clarity in mind. The
operator console uses a split-view: a large live video panel on the left and a high-
contrast status card on the right, so a defect alert is impossible to miss from a few
metres away. The admin Inspection Logs page was wireframed with date filters, metric
cards and Plotly charts so management can review past production without writing
SQL.and receive instant defect alerts without navigating through complex menus.
3.2.3 Implementation Phase (Iterative Development)
The implementation phase was where most of the technical work happened,
and it was split into three iterations. The first iteration focused on the AI core: the
YOLOv8 model was trained on a brake disc dataset annotated through Roboflow,
exported as bestv4.pt, and loaded inside a stripped-down Python script to confirm it
could classify samples reliably.
The second iteration brought in Streamlit and Supabase. The login page,
sidebar navigation, defect detection page, profile page, inspection logs page and user
management page were all wired up to the Supabase client. SHA-256 password
hashing was added in the same iteration. This was also the point where the streaming
layout was tuned: YOLOv8 only runs on every third frame during normal preview,
which keeps the UI smooth without dro

--- PAGE 32 ---
unplugged. This iteration is also where the multi-frame capture logic was introduced:
after receiving SCAN, the backend flushes 10 frames from the webcam buffer (to clear
motion blur and stale frames), captures 5 fresh frames, runs YOLOv8 on each, and
keeps the highest-confidence result.
Following the completion of the third iteration, the dashboard was deployed to
Streamlit Community Cloud for remote access. The application repository was hosted
on GitHub, with Supabase credentials stored in Streamlit's secrets manager rather than
in the codebase. This allowed stakeholders and evaluators to access the software
interface through a permanent public URL without requiring any local installation. It
is worth noting that the live webcam feed and Arduino serial communication are only
functional when the application is run locally on the machine physically connected to
the hardware. The cloud deployment serves the dashboard, analytics, logging, and user
management modules.
One important design decision made in this iteration was the ordering of
database write and motor command. The save to Supabase happens first; the motor
command is only sent if the save succeeds. This guarantees that the physical state of
the conveyor and the database record stay consistent, even if the network drops out for
a moment.
3.2.4 Testing and Evaluation Phase
Testing was carried out in three stages: unit tests, accuracy tests and full-loop
integration tests. Unit tests covered individual components in isolation — the camera
capture function, the Supabase insert function and the Arduino write function — to
confirm each one worked on its own. Accuracy testing fed a held-out set of brake disc
images through the YOLOv8 model to measure precision, recall and mean Average

Integration testing put the whole pipeline together. A brake disc was placed on
the conveyor, the IR sensor triggered the SCAN signal, the webcam captured five
frames, YOLOv8 produced a Pass or Fail decision, the result was written to Supabase,
and the Arduino either moved the conveyor forward or reversed it. This stage is where
the most stubborn issues showed up: serial deadlocks when both ends tried to read at
the same time, brief power brownouts on the L298N when the motor stalled, and
motion blur on frames captured immediately after the IR trigger. The 800 ms sleep and
10-frame buffer flush were added directly in response to the blur problem.
To support real-time performance during testing, the system was run on a
workstation with an AMD Ryzen 5 7500F, 32GB of RAM and an NVIDIA RTX 5060
GPU. This setup kept YOLOv8 inference well under 100 ms per frame, which gave
the conveyor enough headroom to react before the next part reached the sorting point.
